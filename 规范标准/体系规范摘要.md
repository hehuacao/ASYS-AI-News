### 硬约束（不可妥协）

- **同一套 DOM 与同一份渲染实现**：桌面与移动端共用一份页面代码，控件形态随断点切换。
  **禁止为移动端另写页面或第二份渲染函数。**
- **译文只作附加层，永不替换原文**；机器译文出现处必须标注「机器译文 · 未校对」。
- **无横向滚动**：装饰元素一律以 `min(<设计宽度>, 100%)` 收进容器，不得定宽后居中溢出。
- **触达目标 ≥44px**（移动端）。
- **单一实现原则**：同一口径（如排序编号、窗口合并、归组）在管线中只有一个实现位置，
  上下游消费而不重算。

## 体系总纲

### 0. 总纲：体系定位与三部分关联

#### 0.1 体系目的

建立「月生·AI资讯库」每日 AI 资讯的完整运营体系，覆盖从信源获取、信息整理到界面展现的全链路：

- **信源体系**（第一篇）：解决「从哪来」——来源全面、可信、规范、自动
- **信息资源体系**（第二篇）：解决「怎么读」——整理专业权威、体系规范、主线清晰
- **信息展现体系**（第三篇）：解决「怎么看」——展现美观大气、简约便捷、重点突出

#### 0.2 体系结构：三个部分，一条数据流

三部分不是并列的三张皮，而是一条流水线上前后衔接、相互约束的三个环节：

```
[第一篇 信源体系]                 [第二篇 信息资源体系]                [第三篇 信息展现体系]
注册信源 + 抓取流水线    ──▶      打标 + 整理 + 去重分级      ──▶      单文件 HTML 日报仪表盘
原始快照 / 权威度评分    ──▶      A/B/C/D 四维标签           ──▶      L1 总览 + L2 详情两层
信源原始分类透传         ──▶      Event 事件合并             ──▶      深/浅/跟随系统三态主题
```

反向约束同样存在：第三篇规定的详情必备字段，反向要求第二篇的信息 schema 必须携带；第二篇对来源 chip「可信可见」的要求，反向要求第一篇的权威度必须量化。

#### 0.3 三部分关联（接口契约）

| 关联方向 | 契约内容 |
|---|---|
| 第一篇 → 第二篇 | ① 注册表字段（内容域 domains / 地域 region / 国家 country / 语言 language）作为打标输入；② 权威度评分（1–10）作为重要度分级输入；③ 原始快照作为整理与对账基础；④ 信源原始分类原样透传为 C 轨标签 |
| 第二篇 → 第三篇 | ① A 轨主线节点决定 L1 五段结构；② B 轨属性标签决定卡片 chip 与筛选；③ 重要度分级决定头条徽章待遇；④ Event 合并结果决定 L2「相关报道」；⑤ 整理规范（≤60 字摘要、北京时间人话格式、标题不改写）成为 L1/L2 字段标准 |
| 第三篇 → 第二篇（反向） | L2 详情必备字段清单（主线路径面包屑、权威度、验证状态、时间口径标注）反向要求信息 schema 必须携带这些字段 |
| 第三篇 → 第一篇（反向） | ① 「来源可见、可信可见」原则要求权威度必须量化并随卡片展示；② 「原文链接必备」要求注册表必须验证 original 链接可达性 |

## 信源体系

### 1. 总则

### 1.1 目的

建立 AI 资讯信源的体系化管理标准，确保每日资讯的**来源全面、可信、规范、自动**。本篇是信源准入、评价、运维的唯一依据，其产出（注册信源、原始快照、权威度、原始分类）是第二篇信息资源体系的输入。

### 1.2 适用范围

适用于「月生·AI资讯库」每日 AI 资讯流水线的全部信源，包括自动抓取信源与人工巡检信源。

### 1.3 基本原则

1. **官方优先**：同一事实，官方一手信源效力高于任何二手转述。
2. **可追溯**：任何一条入档资讯必须能倒查到信源、抓取时间与原文链接。
3. **免费可自动化优先**：无法免费自动化获取的信源降级使用，不进入自动流水线主干。
4. **合规底线**：不抓取登录墙内容、不绕过反爬、不将社区数据用于训练用途（遵守各平台 ToS）。
5. **动态淘汰**：信源不是终身制，质量不达标即淘汰。

### 2. 术语与定义

| 术语 | 定义 |
|---|---|
| 信源（Source） | 可持续产出 AI 相关信息的渠道，含网站、API、RSS、公众号等 |
| 通道（Channel） | 信源的技术接入方式，分 A/B/C/D 四级（见本章第 7 节） |
| 权威度（Authority） | 信源可信度的量化评分，1–10 分（见本章第 4 节） |
| 原始快照 | 抓取时保存的原文内容 + 抓取时间 + 内容 hash |
| 试用期 | 新信源注册后两周的考察期 |
| 健康度 | 信源可用性的综合指标（见本章第 8 节） |

### 3. 信源分层模型（T0–T4）

分层依据是**信源与事实源的距离**，不是知名度。

| 层级 | 名称 | 定义 | 典型信源 | 流水线权限 |
|---|---|---|---|---|
| T0 | 官方一手 | 事实主体自身发布 | OpenAI / Anthropic / DeepMind / Meta AI / Microsoft / Mistral / xAI / Apple ML / Amazon Science / Hugging Face；Federal Register、Congress.gov、SEC EDGAR、EUR-Lex、网信办 | 可作事实基准；争议事件以 T0 终审 |
| T1 | 学术与基准 | 同行评审或可复现的评测 | arXiv、OpenReview、Semantic Scholar、OpenAlex、HF Papers、Artificial Analysis、SWE-bench、LMSYS Arena、Epoch AI、METR、Stanford HAI | 能力类资讯主证；榜单数据须标注评测方与口径 |
| T2 | 专业媒体 | 有编辑责任的专业报道 | TechCrunch、VentureBeat、Ars Technica、The Verge、MIT Tech Review、Reuters；36氪、量子位、机器之心、新智元、智东西 | 事件叙述主力；须与 T0/T1 交叉后入头条 |
| T3 | 聚合与策展 | 二次聚合与热度信号 | AIHOT、Hacker News、GitHub Releases/Trending、Product Hunt | 热度信号与漏网捕捞；不单独作为事实依据 |
| T4 | 社区与观点 | 社区讨论与个人观点 | Reddit、X、策展博客与 newsletter（Simon Willison、Lil' Weng、Interconnects、Import AI、Latent Space、Alignment Forum） | 只入「观点」类；爆料类须经 T0–T2 验证后才可入正文 |

### 4. 信源可信度与引用评价体系

#### 4.1 权威度评分细则（1–10）

| 分段 | 适用信源 | 评分区间 |
|---|---|---|
| 官方一手（T0） | 实验室官方、监管机构、官方数据库 | 9–10 |
| 学术基准（T1） | 顶会/顶刊、可复现评测机构 | 8–9 |
| 头部媒体（T2） | 有采编团队的专业媒体 | 7–8 |
| 聚合策展（T3） | 编辑策展的聚合站 | 5–6 |
| 社区观点（T4） | 社区高信誉账号、知名个人博客 | 3–5 |

#### 4.2 动态调整机制

- **加分**：连续 30 天无事实性错误且被 T0 交叉验证 ≥3 次，+0.5（封顶 10）
- **减分**：出现一次事实错误（经 T0 证伪）−1；转载失实 −0.5；30 天无更新 −0.5
- **复审触发**：权威度跌出所属层级区间即暂停入头条资格，转人工评估

#### 4.3 引用规则

1. 所有资讯必须链原文（`links.original`），聚合站链接（`links.aihot`）作为补充镜像
2. 引用 T4 爆料时，卡片必须同时展示验证状态（已验证/未验证），未验证不得进头条
3. 中文信源报道英文原始信源时，保留双方链接
4. 信源名称展示用官方名，不使用别称

### 5. 信源分类维度

每个信源挂三个分类维度，用于检索与调度：

| 维度 | 取值 | 说明 |
|---|---|---|
| 内容域 | 模型 / 产品 / 产业 / 治理 / 趋势 / 综合 | 对应第二篇五节点主线 |
| 地域 | 全球 / 中国 | 中国信源重点监控本土合规线 |
| 类型 | 官方 / 学术 / 媒体 / 聚合 / 社区 | 与本章分层模型（T0–T4）对应 |

### 6. 信源注册注销机制

#### 6.1 准入四标准（全部满足方可注册）

1. 免费可自动化获取（或明确的人工巡检通道）
2. 更新频率 ≥ 周更
3. 权威度可论证（符合本章第 4.1 评分区间）
4. 不违反目标平台 ToS

#### 6.2 注册流程

提出 → 通道测试（试抓 3 次，字段完整率 ≥90%）→ 录入注册表 → **试用期 14 天** → 周度评估 → 转正或淘汰。

#### 6.3 注销条件（满足其一即启动注销）

1. 连续 7 个**自然日**真失败且 48 小时内无恢复（"真失败"的判定见 8.1；空结果与环境受限均不算失败）
2. 停止更新超过 30 天
3. 发生事实性错误未更正，权威度跌出层级区间
4. 平台政策变化导致接入违反 ToS（如 Reddit 2025 年底审批制、X 2026 年付费制）
5. 试用期评估不达标

注销动作：从 enabled 列表移除、保留历史档案与注销记录（可审计、可复活）。

### 7. 自动化与人工干预机制

#### 7.1 通道分级

| 通道 | 形态 | 代表 | 自动化程度 |
|---|---|---|---|
| A | 免费结构化 API | AIHOT、HN Algolia、arXiv、OpenReview、Semantic Scholar、OpenAlex、GitHub、HF Hub、Federal Register、Congress.gov、SEC EDGAR | 全自动 |
| B | RSS/Atom | 实验室官方博客、媒体、newsletter | 全自动 |
| C | 受限/付费 | X（$0.005/read 起）、Reddit（审批+禁训练）、The Information（付费墙）、Crunchbase/PitchBook | 不接入主干，人工抽查或媒体交叉替代 |
| D | 人工巡检 | 微信公众号、内幕线索 | 每周人工 15 分钟，只产线索 |

#### 7.2 自动抓取规范

- 统一 User-Agent，明示身份与用途
- 单信源并发 1，请求间隔 ≥2s，尊重 robots.txt
- 失败指数退避重试（3 次），超时 15s
- **每次抓取保存原始快照**（原文+时间+hash）后才进入处理流程
- 每日巡检快照落 `数据/快照/<抓取日>/`；**历史回溯补抓**落 `数据/回溯/<资讯发布日>/`（两者结构一致，归档时同信源 URL 去重且巡检快照优先）。回溯只使用官方接口自带的日期过滤参数（arXiv submittedDate、AIHOT dailies、HN numericFilters、Federal Register publication_date、SEC EDGAR dateRange 等），**不接受按网页猜测或人为补写条目**；不支持历史检索的 RSS/Atom 信源，其历史内容只能来自相邻日期的巡检快照，不另行补足——保证每条资讯都能回溯到一次真实抓取

## 信息资源体系

### 1. 总则

### 1.1 目的

建立 AI 资讯信息的体系化整理标准。以**一条主线**作为分级分类的核心依据，使每日所有资讯都能挂在主线的确定环节上，不同层次的读者沿主线即可完整理解「AI 今天走到了哪一步」。

### 1.2 适用范围

适用于每日资讯流水线的分类、打标、整理、去重、分级全环节。输入为第一篇产出的注册信源与原始快照，输出为携带四维标签的结构化资讯，是第三篇信息展现体系的数据前置。

### 1.3 核心设计原则

1. **主线唯一归属**：每条资讯必选且仅选一个主节点，杜绝「其他」式垃圾桶分类。
2. **原始分类保留**：信源侧的原始分类/分级以标签形式保留，用于展现与检索，不丢失信息。
3. **判定标准先于判定结果**：归类争议按「主要影响落点」规则裁决，不靠个人理解。
4. **整理不失真**：标题不改写、摘要不虚构、时间不模糊、来源不隐藏。

### 2. 术语与定义

| 术语 | 定义 |
|---|---|
| 主节点 | 主线五大环节：能力、产品、产业、治理、趋势 |
| 打标 | 为资讯附加维度标签的过程 |
| 主线标签（A 轨） | 主节点归属，唯一必选 |
| 属性标签（B 轨） | 内容属性，多选 |
| 来源标签（C 轨） | 信源原始分类的保留，只读展示 |
| 地域分区（D 轨） | 全球 / 中国 |
| 来源国家/地区（D 轨附属） | 信源主体归属国家/地区（ISO 3166-1 alpha-2，EU=欧盟），用于国旗区分与跨域汇总；与地域分区相互独立（美国信源亦可发布涉及中国的资讯） |
| 事件（Event） | 多信源报道同一事实的合并单元，保留 source_count |

### 3. 核心主线：AI 产业化价值链（五节点）

**主线定义**：*能力从哪来 → 变成什么 → 谁在投入 → 规则怎么定 → 向哪演进。*

五节点有因果顺序，不是平行分类。读者沿节点顺序阅读，即完成一次完整的产业叙事。

| 序号 | 节点 | 回答的问题 | 今日叙事角色 |
|---|---|---|---|
| 1 | 能力 Capability | AI 的能力边界被推到了哪 | 一切的起点 |
| 2 | 产品 Product | 能力变成了什么可用的东西 | 能力的外化 |
| 3 | 产业 Industry | 谁在投入、谁在赚钱、谁被颠覆 | 产品的商业化 |
| 4 | 治理 Governance | 社会如何回应、规则如何形成 | 产业的约束条件 |
| 5 | 趋势 Frontier | 综合前四者，正在形成的下一个方向 | 指向未来 |

### 3.1 节点一：能力（Capability）

- **是什么**：模型、算法、训练方法、评测基准、算力基础设施的进展，即「AI 能做什么」的证据。
- **判断标准**：资讯的核心信息是某项能力指标、方法或算力条件的变化。
- **边界**：能力「本身」的进展入此；能力「被使用」（应用案例）入产品；能力「被交易」（API 价格）入产业；能力「被约束」（监管）入治理。
- **子类**：前沿模型发布 / 算法与训练方法 / 评测与基准 / 算力与基础设施。
- **纳入示例**：新模型发布、权重开源、新训练范式论文、榜单变化、芯片发布。
- **排除示例**：模型降价（→产业）、某公司用模型提效（→产品）。

### 3.2 节点二：产品（Product）

- **是什么**：能力转化为用户可接触的产品、工具、应用与开源项目。
- **判断标准**：资讯的核心信息是某个产品/工具/项目的发布、更新、修复或落地案例。
- **边界**：产品的「功能」入此；产品的「公司资本行为」入产业；产品的「合规风险」入治理。
- **子类**：新产品与新功能 / 迭代与修复 / 开源项目与工具链 / 垂直行业落地。
- **纳入示例**：ChatGPT 新功能、开源 Agent 框架、某医院部署 AI 诊断。
- **排除示例**：产品背后的融资（→产业）、产品被监管约谈（→治理）。

### 3.3 节点三：产业（Industry）

- **是什么**：资本、市场、组织层面的行为——谁在投钱、谁在赚钱、谁在扩张、谁被颠覆。
- **判断标准**：资讯的核心信息是资金、市场、股权、人事或竞争格局的变化。
- **边界**：产业「商业行为」入此；商业行为引发的「监管」入治理。
- **子类**：投融资与财报 / 并购与合作 / 市场格局与竞争 / 组织与人事。
- **纳入示例**：融资轮、估值、财报 AI 营收、芯片大单、高管离职。
- **排除示例**：产品功能发布（→产品）、反垄断立案（→治理）。

### 3.4 节点四：治理（Governance）

- **是什么**：规则、安全、风险、法律与伦理——社会对 AI 的回应。
- **判断标准**：资讯的核心信息是法规、监管行动、安全事件、判例或伦理争议。
- **边界**：治理对象是「产业与社会关系」；模型自身安全能力研究归能力-算法，模型安全「事故」归此。
- **子类**：政策法规与监管 / 安全与风险事件 / 版权与判例 / 伦理与社会影响。
- **纳入示例**：EU AI Act 进展、算法备案、数据泄露、版权诉讼、深伪诈骗。
- **排除示例**：对齐论文（→能力-算法）、公司财报（→产业）。

### 3.5 节点五：趋势（Frontier）

- **是什么**：跨节点的方向性信号——正在形成但尚未成为主干的新范式与新叙事。
- **判断标准**：资讯的核心信息不是单一事件，而是某方向的观点、研判或早期信号集合。
- **边界**：趋势节点只收「方向性」内容；方向中的具体事件按其主要落点归前四节点。
- **子类**：具身智能与机器人 / 多模态与 AIGC / Agent 与自动化 / 新兴方向与前瞻观点。
- **纳入示例**：人形机器人产业研判、AGI 时间表观点、Agent 范式长文。
- **排除示例**：某机器人厂商融资（→产业）、某视频生成模型发布（→能力）。

### 4. 四维打标体系

#### 4.1 B 轨属性标签词表（封闭词表，新增须修订本规范）

#### 4.2 C 轨来源标签保留规则

- AIHOT：`ai-models / ai-products / industry / paper / tip`

### 6. 标签冲突判定与处理规则

#### 6.1 判定总规则

以「**这条资讯的主要影响落在哪个环节**」为唯一裁决标准。例：模型发布→能力；API 降价→产业；模型被监管→治理。

#### 6.2 优先级

主线节点（A 轨）> 内容属性（B 轨）> 来源标签（C 轨）。C 轨永不覆盖 A 轨判定。

#### 6.3 冲突处理流程（规则 + 内容裁决两层）

1. 规则分类器给出 A 轨候选与置信度
2. 置信度 ≥0.8 → 直接入档
3. 置信度 0.6–0.8 → 内容裁决层：按信息实质（标题 + 摘要 + 信源属性）判归属，入档或显式排除
4. 置信度 <0.6 → 内容裁决层批量处理：入档 / 显式排除（非 AI 内容、会议通稿、与已入档事件重复）/ 事件成员标记（同一 Event 不重复入档）
5. 人工干预模式为「浏览纠错」：日常不逐条人工过队列；仅在浏览仪表盘发现分类错误时，告知后做修正式干预
6. 一切裁决结果回流为判例，写入本章附录 A，并同步改进 classify.py 规则（关键词/先验），使同类内容后续自动判对

### 7. 信息整理规范

### 7.1 时间口径

- 全部转为**北京时间（UTC+8）**展示，人话格式（如「10 月 13 日 01:36」），禁止展示 ISO 字符串
- 时间字段优先级：原文发布时间 > 信源收录时间（须标注「收录时间」口径）
- 慢推信源（官方博客/公众号原文早发、今日收录）按信源收录时间计「今日」

### 7.2 摘要规范

- 摘要 ≤60 字（汉字计），忠于原文信息，不添加原文没有的判断
- 无法压缩保真时截断并标注「…」，禁止为凑字数改写
- 快讯类无原文摘要字段时，不虚构摘要，只展示标题

### 7.3 标题规范

标题使用信源原标题，不改写、不翻译（中文信源原标题即中文）。原标题缺失时以摘要首句代并标注。

### 7.4 去重与事件合并

- 同一事件多信源报道合并为一个 Event，保留全部来源与最高权威度，展示 source_count
- 去重键：规范化 URL + 标题相似度（≥0.85 判重）
- **独立报道口径**：`source_count` 数的是「有**几篇彼此独立的报道**」，不是「有几家登过」。T3 聚合策展站与 T4 社区会把同一篇原文**原样转载**（URL 完全相同），此类转载**只计 1**——否则一篇无人独立报道的稿子会凭一条转载混进交叉热点，并污染头条判定。实现：先按规范化 URL 把成员归并成一篇篇独立报道，每篇只由其中权威度最高的一条作代表，再对代表计信源（`classify._independent_source_ids()` 为唯一实现）。判断某事件是否「真交叉」看**独立报道数 ≥ 2**，不看条数
- **同信源豁免**：同一信源下 URL 不同的两条，即使标题高度相似，也不合并为同一 Event——它们可能是两份独立文档（如 SEC 同日多个不同受理号的同型备案），合并会吞掉真实条目
- **入档唯一代表**：同一 Event 内并入档清单的代表只能有一条（权威度最高，并列时取发布最早）；规则层若对多个信源成员都给出高置信度而全部入档，由 `collapse_duplicate_routes` 统一收敛——其余成员标记 `event_member` 并回填 `event_member_of`，仍在 Event 结构中完整可溯，供交叉热点「N 个信源」使用
- **收敛判据**：`collapse_duplicate_routes` 的收敛条件为「跨信源 **或** 同 URL 重复」——前者管「一个事件只留一条入档」，后者管「同一篇文档不被收两次」。二者与上面的独立报道口径**服务不同问题、不可混用**：转载须在此收敛（否则面板出现重复条目），但计信源时只算一篇
- **跨日不并**：跨自然日的同一 URL 由不同信源分别出版（如 T3 策展源次日转载原文），各自留在所属自然日的数据集内，不跨日删除
- **48h 与 24h 的热点数不可直接相加**：48h 窗口纳入前一日后续报道、并把单日未成交叉的事件合并进来，其热点数**大于**两日 24h 之和属正常口径，不是重复计数；两窗口的正确关系是「48h ⊇ 24h」
- **标题可辨识要求**：同一发行人当天多份同类文档时，标题须携带区分信息（如 SEC 受理号），避免清单里出现无法区分的同名条目

### 7.5 实体命名规范

公司/产品/模型名首次出现用官方名（如「Claude Opus 5.5」不写「Opus5.5」），别名入检索索引。

### 7.6 重要度分级

| 级别 | 判据 | 展现待遇 |
|---|---|---|
| 头条 | 多信源交叉（≥3）或 T0 首发重大事件 | 主线轴徽章 + 卡片强调 |
| 重要 | 权威度 ≥8 或单节点当日前列 | 普通卡片 |
| 一般 | 其余 | 普通卡片，可按筛选收起 |

### 7.7 归档范围与重建规则

**合并范围**：一个自然日 D 的数据集，合并范围 = `D−1` 起至**最新可用快照**的全部快照目录（巡检 `数据/快照/` 与回溯 `数据/回溯/` 同时参与，同信源 URL 去重且巡检快照优先；新快照优先取用，内容更完整）。理由：一次抓取会带回多日历史——D 日的部分内容只会出现在更晚的快照里。只合并 D−1/D/D+1 三天必然残缺（实测 10-14 漏 21 条）。窗口按**发布自然日**过滤，多并入更晚的快照不会混入别日内容。

**重建规则**：每日抓取后按**数据范围**重建，而不是只建当天。受影响自然日 = 全部快照日的 `{S−1, S}` 之并集，由脚本 `脚本/rebuild_days.py` 自动推算并逐日重建（升序），天数不写死、不设上限——快照保留多久就能重建多久。重建后自动复用各日 `<自然日>_自然日裁决.json` 重跑内容裁决；裁决表内的陈旧条目（重建后已不存在）跳过并告警，**不得因此中断整日裁决**。

**队列口径**：「裁决队列为空」不是硬性不变式——更宽的合并范围会持续带入新发现的当日条目，其中一部分落在人工队列属正常，由「浏览纠错」逐步裁决。硬性要求只有一条：队列条目的 ID 必须都在数据集内（完整性）。

**快照是唯一重建事实源**：`数据/快照/` 与 `数据/回溯/` 是**唯一能重建某自然日的数据来源**——日报 JSON 是可再生的产物，删掉它可以重建；删掉快照目录则该日永久无法重建。因此快照目录**不得手工删除**，确需收敛体积时走脚本的显式清理命令（`rebuild_days.py --prune-snapshots --keep-days N`，默认只预览清单、显式加 `--apply` 才真删），保留期按 **90 天**执行。**快照保留多久，就能重建多久。**

### 7.8 结构性噪声闸门

**问题**：SEC EDGAR 是**全文检索**源——只要申报正文出现过 "artificial intelligence" 就命中，于是模板化的基金说明书（424B2 / 485BPOS / 497K / N-2 / ARS）、持仓与股权申报（13F-HR / SC 13G）、股东会与代理声明（DEF 14A / DEFA14A），乃至大盘股的程序性 8-K / 10-K，都会成批带回；其 AI 只存在于风险因素模板段落。实测这类条目占当日入档约 1/4，且数量随大盘申报节奏跳动（10-13 有 87 条、10-14 有 62 条，而 10-11/10-12 为 0），严重干扰日报口径与跨日可比性。

**判据**：`SEC 条目` 且 `标题与申报说明均无 AI 主体词` → `route = excluded` + `noise_reason`。

- **为什么用「AI 主体词」而非节点关键词**：SEC 条目的标题由机器拼装（发行人 + 日期 + 表单号 + 受理号），不含正文语义；发行人名里的 `Investment` / `Acquisition` / `Data` 等金融通用词会命中节点词表造成假信号（实证：JPMorgan 424B2 曾凭 "investment" 拿到 0.95 自动入档）。故本闸门只看 AI 主体词表（`classify.AI_SUBJECT_RE`）。
- **不误伤的边界**：真实与 AI 相关的备案（如 AI 主体公司的 S-1/8-K、申报说明含 AI 主体词）不受影响，正常进入分类流程。
- **可追溯、可反悔**：被排除的条目**完整保留在数据集内**（带 `noise_reason`，注明表单类型与原因），不进日报、不占人工队列；放宽只需在 AI 主体词表增词，不需改流程。
- **规则层权威**：`adjudicate.py` 跳过带 `noise_reason` 的条目，人工裁决表**不得翻案**，避免旧裁决把已排除的程序性备案拉回。

### 8. 信息展现必备要求（对接第三篇）

1. 每条资讯卡片**必备字段**：标题、摘要、主线节点路径、来源 chip（含权威度）、北京时间、原文链接
2. **禁止事项**：隐藏来源、模糊时间、改写标题、虚构摘要、把聚合站链接当原文链接
3. 无法归类的资讯必须进待归类池，**不得强行入箱**
4. 某主节点当日无料时展示明确空态，不用相邻节点内容填充

## 信息展现体系

### 1. 总则

#### 1.3 展现四原则（不可妥协）

1. **不失真**：摘要、标题、数据必须与信源原文一致，不夸大、不弱化
2. **不篡改**：不修改原标题、不虚构摘要、不模糊时间、不隐藏来源
3. **来源可见**：每条资讯的信源与原文链接必须可见可达
4. **可信可见**：信源可信度（权威度/验证状态）必须随内容展示

### 7. 技术形态约束

- **无第三方运行时依赖**：不引用 CDN、外部字体服务或第三方脚本，字体用系统字体栈；主题用 CSS 变量整体切换；可嵌入 iframe，保持响应式
- **产物双形态**：
  - **离线产物（默认分发）** `仪表盘/ai_news_daily.html`——样式、脚本与**全部投影**内联，零网络请求；双击即可用，用于分发、存档与无数据服务的环境
  - **运行态产物** `仪表盘/runtime_shell.html`——薄壳（外壳 + 样式 + 渲染函数 + 内联索引与最近完整日 24h 兜底），数据在运行时从 `数据/视图/` 读取，数据更新后刷新即呈现新内容，无需重新生成页面（**须经 HTTP 访问**）
- **运行受限环境降级**：运行态页面启动时按**候选根**探测数据源（`../数据/视图/` → `数据/视图/` → `./数据/视图/` → `/数据/视图/`，取第一个返回合法索引者并固定）。探测不到时分两种情形给出**可操作的提示**而非静默失败或泛泛报错：以 `file://` 直接打开（浏览器禁止页面读本地数据文件）时**不发起请求**、直接以内联首屏兜底；经 HTTP 但数据目录不可达时提示相对位置不符。两种情形均自动改用内联首屏数据渲染（功能不缺失，仅不自动更新），并提示改用离线单文件版；月历中当期取不到数的日期标为不可切换、点选时说明原因
- 数据以投影文件（见 8）承载，L2 由内存数据渲染，无路由跳转

### 8. 运行架构：数据源驱动（数据与展现分离，v1.6）

#### 8.1 四层数据流（依赖只向下，无反向依赖）

| 层 | 职责 | 产物 / 接口 |
|---|---|---|
| L0 采集层 | 抓取原始内容，只保存不改写 | `数据/快照/<抓取日>/`、`数据/回溯/<发布日>/` |
| L1 加工层 | 分类、打标、去重、事件合并、内容裁决 —— **唯一事实源** | `数据/日报/<自然日>.json` |
| **L1.5 译文层** | 预生成标题/摘要对照译文（**可再生缓存**，非事实源；缺失不阻塞投影） | `数据/翻译/译表.json` |
| L2 视图投影层 | 把事实源翻译为展现语义（前端不必理解业务字段），24h/48h 合并口径在此**唯一实现** | `数据/视图/index.json`、`数据/视图/<日期>_<窗口>.json` |
| L3 展现层 | 只读投影、渲染与交互，**不持有数据副本** | `仪表盘/ai_news_daily.html`（薄壳） |

**L1.5 译文流水线**：`脚本/translate_items.py` 读 L1 全部入档条目 → 按语言判定分向（英→中 / 中→英）→批量调用文本模型（OpenAI 兼容接口，密钥走环境变量 `AGNES_API_KEY` 或用户目录配置，**绝不入库**）→以「条目 id + 原文指纹」增量缓存到 `数据/翻译/译表.json`。约束：
- 译文是**派生产物**：可整体重跑再生；单批失败只丢该批；**人工定稿（`reviewed`）后不再覆盖**。
- **增量判定须同时满足「原文未变」与「译文齐全」**：只比原文指纹（`src_hash`）会把「模型漏返回某个字段、但记录已落盘」的情况永久跳过——该字段此后永不再译。译文齐全 = 原文有内容的每个目标字段（标题 / 摘要 / 摘要全文）在译表中均有非空译文；人工定稿优先，不覆盖。
- 提示词硬规则：忠实原文不增删事实、专有名词/数字/单位照抄、空字段输出空串、只输出 JSON。
- 译表缺失时投影照常进行（无对照层），**不得让双语成为数据链路的单点依赖**。

#### 8.2 视图契约 VIEW-01

- `index.json`：`schema`（VIEW-01）、`spec_version`、`latest`（最近完整自然日）、`days{ <日期>: {24h, 48h, live, generated_at, sha256} }`、`windows`
- `<日期>_<窗口>.json`：`schema`、`date`、`window_hours`、`stats`（入档 / 信源 / 涉及中国 / 头条 / 热点 / 按节点 / 按国家 / 按属性标签）、**`nodes`（五节点：顺序即价值链推进顺序，含中文名/英文名/定义/计数/头条数）**、`hot_events`、`items`（条目展示字段全集，**已按展现顺序排列并带 `num` 序号**）
- 投影条目字段（**白名单，禁止增删业务字段以外内容**）：`num` / `id` / `title` / `summary` / `summary_full` /
  `summary_compressed` / `node` / `node_name` / `subcategory` / `importance` / `source_id` / `source_name` /
  `source_tier` / `authority` / `country` / `country_name` / `region` / `published_bj` / `time_basis` /
  `url` / `mirror_url` / `tags_b` / `tags_c` / **`hot_event`（本条作为入档代表所属的事件 id，无则 null）/ `hot_sources`（该事件独立信源数，无则 0）** /
  **`lang`（原文语言 zh/en，判据：汉字占比 ≥20% 或 ≥2 个汉字）/ `title_alt` / `summary_alt` / `summary_full_alt`（L1.5 译文，对照层，可空串）/
  `alt_reviewed`（人工已校对标记，**稀疏字段**——仅 true 时出现）**
- 视图级 `translation` 字段：`{provider, model, at, items, reviewed}`——译文元信息**汇总**在视图级，
  逐条重复同一份 provider/model 没有意义
- 热点事件条目字段：`event_id` / `canonical_item`（**本视图内承载该事件的入档条目 id，即「热点定位到面板」的落点**；本视图无入档条目时为 null）/ `canonical_title` /
  **`canonical_num` / `canonical_node` / `canonical_node_name`（落点的当日序号与所属环节，供热点条目尾部的「环节 · 序号」按钮直读）** /
  **`canonical_title_alt` / `canonical_lang`（热点标题的对照译文，取自入档代表条目——与卡片同一份译文，禁止两处各取）**/
  `source_count`（**独立信源数**，同一信源只计 1）/ `source_ids` / `china` / `members`（**逐条报道**明细：`item_id` / `source_id` / `source_name` / `authority` / `url` / `country` / `country_name` / `region`）
- **事件与卡片的对应关系**：`canonical_item` 与卡片上的 `hot_event` 互为反向索引——热点条目据此定位到面板卡片，
  卡片据此回跳热点条目。事件若在本窗口没有入档条目（成员待裁决/待归类），`canonical_item` 为 null，
  热点条目显示「未入档」，面板中确实没有对应卡片（不是渲染遗漏）
- **展现语义下沉 L2**：条目顺序（节点 → 重要度 → 时间新→旧）与 `num` 序号由 L2 唯一确定（`display_order`），渲染层只消费不排序——离线单文件与运行态薄壳因此天然同序同号，逐段比对才有意义
- 投影**不含 SVG / 颜色 / 布局**等表现层内容：国旗等由展现层按 `country`（ISO 3166-1 alpha-2）自行绘制；**表现层「定义型资产」**（国旗画法 / 国家中文名 / 节点元数据 / 信源分层名）由 `脚本/gen_runtime_assets.py` 从 Python 单一实现导出为 `脚本/assets/runtime_assets.js`，两套产物共用同一份定义，禁止各写一套
- `index.days.<日期>.windows.<窗口>` 记 `filed` / `bytes` / `sha256`：页面据此判数据新旧与完整性，无需整文件比对
- 契约带版本号：字段增删不破坏旧页面；前端只依赖契约，不依赖实现
- **禁止**前端自行推算业务口径（节点归属、地域判定、重要度、24h/48h 合并、排序与序号一律由 L1/L2 产出）

### 10. 打包 · 部署 · 发布与持续运营

#### 10.1 最小部署集与三类更新

| 文件 | 角色 | 变更频率 |
|---|---|---|
| `index.html` | 展现文件（运行态薄壳：外壳 + 样式 + 渲染函数 + 内联索引与首屏兜底） | 改版时 |
| `数据/视图/index.json` | 数据索引（各日双窗口条数、最近完整日、sha256） | 每日 |
| `数据/视图/<日期>_<窗口>.json` | 单日单窗口投影（VIEW-01） | 每日（历史不变） |

- **首次部署**：上传整包（展现 + 全部数据）。
- **日常运营（只更数据）**：上传 `数据/视图/` 即可，界面无需重发。前一日投影一旦生成即不再变化，
  故可用增量同步；索引 `index.json` 每日必换。
- **界面改版（只更界面）**：上传 `index.html` 即可，数据无需重发。
- 目录相对位置是**契约的一部分**：`index.html` 与 `数据/视图/` 必须保持上述相对关系
  （页面会按候选根探测 `../数据/视图/`、`数据/视图/`、`./数据/视图/`、`/数据/视图/`，命中即固定）。

#### 10.2 一键打包（`脚本/release.py`）

```
python 脚本/release.py                # 完整包（界面 + 数据）→ 发布/ai_news_daily-<日期>/
python 脚本/release.py --mode data    # 只打包数据（日常运营）
python 脚本/release.py --mode shell   # 只打包界面（改版发布）
python 脚本/release.py --zip          # 额外产出 zip 便于传输
```

包内结构：

```
ai_news_daily-<日期>/
  index.html           部署根文档
  数据/视图/*.json      投影数据（index + 各日 24h/48h）
  release.json         发布清单：契约版本 / 规范版本 / 数据日期范围 / 文件 + sha256 + 字节数
  部署说明.md           三步上线、更新方式、回滚方式
  本地预览.py           零依赖静态服务（python 本地预览.py 8765）
```

**打包前强制校验**（任一不过则中止，`--no-verify` 可跳过但不建议）：数据审计 → 投影校验 →前端资产与 Python 定义一致。校验通过后才会生成包，避免「把有问题的数据发上线」。

#### 10.7 解耦承诺（界面与数据互不牵连）

数据与界面只通过 **VIEW-01 契约**耦合，因此：

- **契约向后兼容**（新增字段）：界面可先发或后发，两种顺序都能正常工作
- **契约不兼容变更**（字段改名/删除/语义变更）：必须同版本界面 + 数据一起发布，
  并在 `release.json` 的 `spec_version` / `schema` 中标注，供运维判断能否分开更新
- 展现层不得回读 L1 事实源、不得自行推算业务口径（§8.2）——这是「只更数据」得以成立的前提
